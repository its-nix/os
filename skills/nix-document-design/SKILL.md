# Nix Document Design

**Inert first-party candidate: not installed, approved, or deployed.** Initial proposal is task-only for a bounded LNX/default document-design task, not a persistent role skill or blanket specialist installation. No plugin, credential, network fetch, or profile mutation is required by this candidate.

1. Lead with one specific H1 and an answer-first summary. Put validity and consequential caveats in visible prose, not only frontmatter or color.
2. Build a semantic H2/H3 hierarchy with short paragraphs, parallel lists, concrete examples, and deliberate whitespace. Use small comparable tables; move long narrative cells into sections.
3. Use restrained native callouts only when their ordinary blockquote fallback retains every instruction. Never collapse critical evidence or risk.
4. Prefer stable filenames, standard relative `.md` links, descriptive labels, image alt text, and a small useful map of content. Search before creating duplicates; keep project detail at its canonical source.
5. Add Mermaid only when it explains a relationship better than prose. Include an accessible adjacent text alternative; verify syntax and both intended renderers before claiming visual acceptance.
6. Follow the KB's actual frontmatter/lifecycle contract rather than inventing task-status fields. Writing polish does not turn provisional content into truth.
7. Check headings, frontmatter, links, fences, diagrams, narrow-screen readability, and visible validity in GitHub and Obsidian. Report untested renderers explicitly.

Read [portable Markdown patterns and verification](references/portable-markdown.md) before authoring. Bases is an optional view of canonical note properties, never a required reader dependency, approval store, task manager, or privacy boundary.

Presentation changes do not authorize factual promotion, publication, skill installation, external-directory configuration, or identity/memory edits. Use the repository contribution contract and Lead routing for substantive changes.
