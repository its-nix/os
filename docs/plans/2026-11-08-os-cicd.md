# Tracked VPS deployment plan

> Execute inline using executing-plans. The user requested merging the completed work and adding OS CI/CD; no additional approval round is needed.

**Goal:** Every passing main-branch deployment is tied to a Git commit and a GitHub Actions run, with daily reconciliation.

**Design:** Extend existing CI with a main-only deployment job on GitHub-hosted runners. Connect as a dedicated `nixops` operator through an environment-scoped, forced-command SSH key. A root-owned launcher accepts only the current public OS main SHA, serializes deployments and executes that revision's deployment script. Compose uses immutable image pins and existing native state. The operator's human key supports normal SSH and Docker administration; this account is an administrator, not a container sandbox.

**Boundaries:** No provider login, agent activation, old-state import, self-hosted runner or backup publication. Preserve memories, credentials, profiles and controller databases. Company KB, Kit, role and profile changes require an explicit state refresh; deployment refuses mismatched installed inputs rather than silently replacing them. Runtime image upgrades must pass native health and KB checks. A failed rollout remains visibly failed; no automatic database rollback is attempted.

## Review focus

- A PR or non-main ref cannot receive deployment credentials or invoke the host.
- An old queued SHA cannot roll back newer main.
- A failed command cannot overwrite the successful receipt or claim healthy state.
- No state directory is created, replaced or recursively reowned during deployment.
- Every native input change is applied explicitly or refused with a useful reason.
