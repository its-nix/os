# Nix portfolio monitoring

## Architecture

`collector.py` discovers runtime profiles/boards from Hermes and tasks from each known board database using a bounded, immutable checkpoint-only SQLite reader. It never calls Kanban task-list or diagnostic commands, because those can recompute derived state or perform SQLite coordination writes. A non-empty WAL, unsafe/missing database, source change, malformed row, or row cap returns explicit `unavailable`/`partial` status; the monitor must not treat missing rows as zero or bypass the status. This deliberately chooses literal zero observer-side filesystem writes over visibility of uncheckpointed WAL-only updates. `task_read_mode` and per-board status explain the constraint. Worker diagnostics are currently unavailable through a verified passive export and therefore remain UNKNOWN. Only manifest-governed projects/roles are actionable; runtime-only boards/profiles are unclassified. Paused/archived scopes are excluded. Task output omits bodies, comments, logs, session data, paths, and credentials. Repository check collection uses only explicitly mapped repositories; the 1,000-PR cap and malformed rows are `partial`, failed probes are `unavailable`, and unknown states are never zero or healthy. Visible task completion counts are observed snapshots, not historical throughput where archived records are omitted.

`monitor_snapshot.py` compacts the collector output into a bounded, stable, sanitized JSON snapshot for Hermes Cron. It includes project/role scope, explicit board/task/repository collection status, read mode and observed-row counts, aggregate task counts, up to ten blocked/stale task identifiers per project with a full finding count and digest, worker-health status, declared KPI values only, repository check aggregates, and timestamp-free stable event keys. It omits changing task ages so unchanged findings remain byte-stable. The weekly `executive_snapshot.py` renders the same evidence but never refreshes the 12-hour monitor heartbeat. If snapshot generation fails or exceeds its output bound, the monitor heartbeat is not refreshed. No KPI targets or values are inferred; absent declarations and failed queries remain UNKNOWN.

## Schedules and recovery boundaries

`jobs.json` declares a 12-hour Hermes monitor job in built-in monitor-script mode and a separate Monday 10:00 local-time executive summary. The executive summary is distinct from Hermes's existing Monday usage review. Both target the configured Discord DM and use continuity plus stable event identities for deduplication. These are candidate definitions; this change has not activated live jobs or the watchdog.

`reconcile.py` is preview-only by default. It reads the selected profile's cron list through `hermes cron list --all`, refuses same-name drift, duplicates, paused/disabled jobs, and any manifest shape outside the reviewed allowlist. Before apply it reads back `approvals.mode`, `approvals.cron_mode`, and `kanban.dispatch_in_gateway`, requiring `manual`, `deny`, and `true`; it installs only missing managed script copies using no-follow, owner/mode-checked paths and creates only missing jobs using supported CLI flags. It never edits, resumes, deletes, enables, or runs an existing job. Do not apply until the exact candidate is reviewed, merged, and approved for runtime rollout. After approval, preview and read back the exact job names, scripts, schedules, destinations, and continuity settings.

`recovery.py` is a pure deterministic proposal/readback validator; it never invokes Hermes, GitHub, or a subprocess. It resolves only uniquely governed active projects and declared Leads, checks fresh source evidence, and creates a stable idempotency key from the stable event key plus action. The proposal carries a two-distinct-attempt work bound and `max_retries: 2`; in Hermes, `max_retries` is specifically the consecutive worker-spawn failure breaker, not the work-attempt count. A scheduled monitor may report the approval-required handoff, but must not create a task. Any later task creation requires an approval-gated native Kanban tool; direct CLI or subprocess creation from the scheduled job would bypass the manual approval boundary. Readback validation checks the governed board, Lead, task ID, stable idempotency key, exact retry cap, and marker. Independent success requires fresh source evidence collected after the recovery task completes. Keep `approvals.mode: manual`, `approvals.cron_mode: deny`, and `kanban.dispatch_in_gateway: true` unchanged. The monitor cannot edit project code, change runtime/configuration/credentials, merge, deploy, or contact customers/banks.

## Independent watchdog

`watchdog.py` is designed to run as a user-systemd oneshot every minute, outside the Hermes gateway. It checks the gateway service, scheduler ticker heartbeat, monitor cron job's last-run age/status, and sanitized collector heartbeat. It sends one deduplicated critical email per changed failure set using `gws`, from `lclaw.agent@gmail.com` to `lior3226@gmail.com`; healthy state clears the dedupe fingerprint. It does not restart services or mutate Hermes. State is held under `${HOME}/.local/state/hermes-monitoring/`, not Git. Unit/timer files are source-only; install/enable only after the candidate is reviewed and a separately authorized rollout is approved. A user-session watchdog cannot alert while the entire user session or machine is unavailable.

## Verification and limitations

Synthetic tests cover dynamic project discovery, unclassified runtime scope, pause/archive exclusions, task states and staleness, stable event identity, output sanitization, immutable checkpoint-only reads, active-WAL fail-closed behavior, source/sidecar non-mutation, symlink rejection, snapshot behavior, cron reconciliation, recovery proposal/readback validation, and watchdog failure states. A synthetic fixture is not a live scheduled run. Before activation, run one sanitized live snapshot, verify governed scope and coverage statuses, preview cron reconciliation, verify systemd unit syntax, and independently review the exact candidate. After an authorized rollout, read back exact jobs and timer/service state and verify one successful cycle and delivery.

Current KPI coverage is intentionally incomplete: the governed manifest does not declare KPI definitions/sources/windows/thresholds for all projects, so undeclared values remain UNKNOWN. An authorized aggregate-only MeaBeclick read supports future metric work but is not a scheduled input. Pulse targets remain UNKNOWN. The Algua Lead inventory attempt was blocked by approval policy; its documentation-only inventory does not establish live KPI values. Worker diagnostics remain UNKNOWN until a verified passive source is available; aggregate counts, when available, are signals rather than root-cause proof.
